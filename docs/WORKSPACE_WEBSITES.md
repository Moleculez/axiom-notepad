# Workspace websites

A workspace can publish a small research website without exposing its private
workbench. Open **Workspace → Website** to create a private draft. Personal
workspaces use a researcher identity; group workspaces use a team identity.
There is no commerce, public account registration, plugin installation or arbitrary
HTML/JavaScript injection. This is a structured publishing system, not WordPress parity.

## Draft, review, publish

1. A workspace manager creates the website, choosing a unique address and title.
   Its built-in address is `https://YOUR-APP/sites/YOUR-SLUG/`. Creation is private.
2. Editors select existing workspace resources under **Content** and classify them
   as posts, pages, papers or resources. Public titles, summaries, tags, dates,
   author credits, DOI, license and cover images are independent of private names.
3. Add supporting images/files explicitly. A linked private file does **not** become
   public just because a published note mentions it. Add public author profiles
   manually; account biographies, email addresses and group membership are not
   copied automatically.
4. Arrange the site under **Design**. Scholar, Notebook, Lab and Journal layouts
   are independent of seven visual themes, including LaTeX Paper and Monograph.
   Choose light/dark/system mode, accent, density, reading font and typography;
   add, reorder, duplicate or hide sections.
   Sections include introduction, featured work, publications, posts, people,
   research, gallery, resources and Markdown. Navigation supports selected pages
   and explicit HTTPS links.
5. Save the draft, then request **Review & publish**. The worker builds a frozen
   preview from the selected saved versions. Unsaved local edits are not included.
   The live design specimen uses the publication renderer and CSS, with a sample
   article or your draft homepage. The frozen review contains the selected sources.
6. A manager reviews that preview, its warnings and explicit publication checklist,
   then approves the matching release/fingerprint. Editors can prepare previews but
   cannot publish, roll back, export the site or change its domain.

Publishing changes one live-release pointer. Editing a note, changing a website
draft or building a new preview does not update the live website. A failed build
leaves the previous release intact. Managers can unpublish immediately or review
and restore a previously published release. Private preview URLs require current
workspace access, are marked noindex/no-store and do not work anonymously.

The CMS shows the latest 100 published releases, the current live release, and all
unpublished drafts. Up to 100 unpublished review drafts can be retained; remove
unused drafts from Review & publish to free capacity. Previously published
releases remain for rollback and are not individually deletable in this version.
All generated bytes count against storage, including local reader libraries in
each release. Keep an eye on **Settings → Storage → Management**.

## Publication is a separate copy

- Private notes, drafts, suggestions, annotations, discussions, audit data and
  account/session details are not added to the public runtime.
- Published source content stays public if its private source is moved, trashed
  or permanently deleted. A later release can retain the last published copy;
  its preview displays a warning. It cannot read the moved/deleted private file.
  Remove the entry/supporting asset from the website draft and publish again to
  withdraw that content, or unpublish the whole website.
- Native Markdown/Canvas downloads and original binary downloads are **off by
  default**. Opting in exposes the complete selected source, including any
  embedded metadata or hidden content. Previously unavailable originals cannot be
  recovered from a flattened public preview.
- Trashing a workspace or its group suspends its website. Restoring the workspace
  does not republish it; a manager must explicitly approve a release again.
  Permanent workspace deletion removes releases and queues their blobs for cleanup.
- Public HTML, CSS, readers, fonts and assets are served from a release manifest,
  independently of the authenticated workspace shell. Only the live release is
  anonymously routable. The app's service worker does not cache public websites.
- Unpublishing prevents subsequent requests to this server. Downloads, exports,
  screenshots, browser history and copies retained by other people cannot be recalled.

## Public research readers

| Content | Public treatment and limits |
| --- | --- |
| Markdown | Read-only research typography, headings/outline, tables, code, citations, footnotes, MathJax SVG equations and locally loaded Mermaid diagrams. Raw HTML is inert; unavailable private links and remote images are omitted. |
| Math | Rendered equation, TeX copy and SVG download. |
| Canvas | Read-only cards/connections, pan, zoom, Fit and card search. File cards link only to explicitly selected public resources; nested canvases open their public page. |
| Images / image projects | Flattened PNG with orientation applied and metadata removed; double-click/Enter opens an inspection viewer. SVG is rasterized from a restricted vector subset, so check the preview for differences. Image projects publish their flattened preview, not layers. |
| PDF | Local PDF.js reader, page navigation, zoom, outline, fullscreen and next-matching-page search. No private annotations or collaboration UI. **The complete PDF bytes, including embedded metadata/annotations, are public.** Inspect/redact the original first. |
| Audio/video | Browser playback and byte ranges. Complete media bytes/metadata are exposed; codec support depends on the browser. |
| Text / CSV / TSV | Escaped text and simple bounded tables; text preview is limited to 5 MB and delimited tables to 1,000 rows. |
| DOCX / PPTX | Inert text/headings/tables, visible slide content. Tracked deletions, comments, speaker notes and hidden slides are not published by the preview. No layout-perfect Office conversion. |
| XLSX | Visible sheets and visible row/column values only; formulas, comments and hidden data are not included. Only cached formula results are available. |
| Other files | No generic binary execution or iframe embedding. An original download is available only if a manager explicitly approves it. |

Image/Office preview inputs are bounded at 50 MB; images at 40 megapixels.
A release accepts up to 2 GB of selected files and 25 MB of snapshot text, produces
at most 3 GB, and has a five-minute build limit. Large public PDFs search at most
1,000 pages per request. These readers are intentionally smaller than the private
research workbench: no editing, saved private reading state or PDF annotation layer.

Public pages include print styles, canonical URLs, author/tag/archive pages,
local metadata search, citation metadata, RSS and a sitemap. No analytics or
external AI calls are enabled by publication. Search covers published entry metadata,
not every embedded document's full text.

## Reading, themes and discovery

New websites start with **LaTeX Paper**: locally hosted Latin Modern, paper-like
proportions, restrained section rules, booktabs-inspired tables and mathematical
typography. Existing configurations without a theme retain **Original**. Additional
styles are **LaTeX Monograph**, **Tufte Essay**, **Material Research**, **Fluent Studio**
and **Minimal Journal**. These change component shape, spacing and typography, not
just accent colors. They are Axiom implementations inspired by those design
traditions, not integrations with Material or Fluent component libraries.

Design → Reading & discovery controls text size (16–24px), line height, line length,
section numbers, word count, estimated reading time, TOC and progress. The TOC
follows heading ancestry, highlights the current section, folds branches, and
collapses into a disclosure when the desktop is too narrow for a side rail.
Heading copy buttons share stable section URLs without search parameters. In the
Tufte theme, sufficiently wide pages also display collision-aware margin footnotes;
ordinary endnotes remain available at every width and in print.

Markdown statistics use the shared document engine. Code/TeX syntax is not counted
as prose. Binary files do not receive invented word counts.
Language-tagged code fences retain server-rendered syntax highlighting in theme
specimens, hosted pages and static ZIPs. Public token colors adapt to light/dark
mode and print; unsupported languages remain escaped, readable plain code.
Topics have an index, search and publication counts; articles include related work
and newer/older links.
The archive groups entries by year and month, with search, author, topic and content
filters encoded in its URL. Ordinary pages are excluded by default but can be
included. Use an explicit entry date when appropriate; otherwise the first approved
publication date is retained across later releases and rollbacks.

These reading changes require a newly built, reviewed and published release.
Existing frozen releases are not rewritten automatically.

## Author analytics and privacy

**Website → Analytics** is private to workspace editors and managers. It includes
7/30/90-day or custom date ranges (up to 397 days), comparison with an equally long
preceding period, author/topic/type/article filters, a chart with equivalent daily
data, CSV article export, article and coauthor tables, referring domains, publishing
cadence and research-content totals. Editorial totals describe the current live
release, independently of the readership date range. Coauthors each receive full
credit; site totals count a shared article once.

Only managers can change **Collection & disclosure**. First-party analytics start
**disabled**. Enabling collection does not republish content; disabling it fences
subsequent server writes immediately. Public article view/download-click totals and
site-footer totals are separate, explicit disclosures. They are lifetime counters
for currently published entries, not access to private dashboard data.

Metric definitions:

- **Views** count page loads, not unique people.
- **Engaged views** have at least ten active seconds.
- **Scroll completions** combine 90% article depth and ten active seconds.
- **Active seconds** accrue while visible and recently active, capped at thirty
  minutes per page instance. Download/citation/outbound figures count actions;
  download clicks are not verified completed transfers.

The first-party collector uses no tracking cookies, raw IP storage, fingerprint,
account identity or persistent visitor identifier. A random in-memory page token
deduplicates cumulative/retried events. Referrers are reduced to domains; paths,
query strings, search terms and article text are not accepted as metric fields.
Known bot user agents, previews, Do Not Track, Global Privacy Control and visitor
opt-out are excluded. Public signals can still be fabricated or blocked: these
are approximate readership indicators, not proof of human readership.

The worker deletes ephemeral per-page deduplication rows after seven days and daily
aggregates after thirteen months; public lifetime counters remain. Requests are
size-bounded, origin-checked, validated against the current live manifest, and
rate-limited per site per serving process. For horizontally scaled deployments,
add a shared edge rate limit. Infrastructure/proxy access logs are separate from
the application analytics tables and have their own retention policy.

Optional **Google Analytics 4** accepts only a measurement ID (`G-…`), never a script.
Google code/network requests are blocked until explicit visitor acceptance; rejection
is as accessible as acceptance. Advertising storage and signals stay disabled.
Visitors can reopen Privacy settings to withdraw consent; browser privacy signals
disable both collectors. Preferences, not visitor IDs, are saved locally for up to
180 days. A changed Google ID requires fresh consent. Removing an ID is reflected
on new loads and existing visible pages during the one-minute configuration poll.
GA reports remain in Google; no OAuth connection or report import is provided.
See [Google consent documentation](https://developers.google.com/tag-platform/security/concepts/consent-mode).

Local development collects nothing unless an isolated acceptance service explicitly
sets `SITE_ANALYTICS_LOCAL_TEST=1`. Never enable this for routine development. The
visitor opt-out governs first-party counting without an initial consent prompt;
site operators remain responsible for their disclosures and applicable obligations.

## Static ZIP export

In a ready release's review dialog, expand **Export a static website** and enter its
final HTTP(S) base URL, including a deployment subdirectory if needed. The ZIP
contains static HTML/assets, locally bundled readers/fonts, licenses and hosting
notes; private snapshots, credentials and server APIs are absent.

First-party event collection and live aggregate counters are omitted. The review
dialog has an unchecked **Include configured Google Analytics** option. Selecting
it includes only the configured measurement ID and consent-gated loader, with CSP
instructions in `HOSTING.txt`; it never automatically grants visitor consent.

Extract it into a static host configured for directory `index.html` files and
serve it over HTTP(S), not `file://`. Keep `_site/` and its hashed chunks together.
Canonical URLs, RSS and sitemap use the entered base URL. Configure the generated
404 page and your host's security headers yourself. Exported websites are
independent copies: Axiom cannot revoke them or update them automatically.

## Built-in hosting and custom domains

Migration **33** (including 32), matching web/worker/publish code and `npm run publish:assets`
are required. `npm run build` and `npm run dev` prepare those assets automatically.
The background worker builds releases. During development Next serves the built-in
`/sites/…` route; production Compose additionally runs the independent **publish**
service. It reads the same database/storage but serves no authenticated workbench.

For custom domains with the supplied Caddy deployment:

1. Point a dedicated public hostname, such as `sites.example.org`, at the server.
   Set `PUBLISH_DOMAIN_TARGET=sites.example.org` in the production environment
   and recreate the matching services. It is a hostname, not a URL.
2. Under **Website → Domain**, add the desired hostname. Each website supports
   one custom hostname; a hostname can belong to only one website.
3. Add the exact ownership TXT record shown at `_axiom.YOUR-DOMAIN`, and point
   the hostname's CNAME at `PUBLISH_DOMAIN_TARGET`. For an apex domain, all A/AAAA
   addresses must match the target's addresses. Remove obsolete IPv6 records.
4. Click **Verify DNS** after propagation. Verification checks DNS ownership and
   routing without fetching arbitrary HTTP endpoints. Verification is manual;
   ongoing ownership/DNS drift is not periodically rechecked in this version.
5. Approve a release. Caddy asks the private control endpoint whether that hostname
   is verified, enabled and attached to an active/archived workspace before issuing
   an on-demand certificate. Certificate issuance still requires reachable public
   ports and successful CA validation. See Caddy's [on-demand TLS documentation](https://caddyserver.com/docs/automatic-https#on-demand-tls).

The supplied custom-host catch-all proxies **only** to the publication reader.
Unknown/unverified hosts never fall back to workspace/login routes. A verified
domain becomes canonical; the built-in site URL redirects to it. Disconnecting it
restores the built-in URL. A failed DNS check leaves the existing mapping unchanged.
Your application login hostname cannot be assigned as a website hostname.

Compose publishes reader port 3001 only on host loopback; change
`AXIOM_PUBLISH_HOST_PORT` if occupied. Port **3002 is internal certificate
authorization and must never be publicly proxied**. Native systemd uses
`axiom-publish.service` and the supplied native Caddy configuration.

If retaining host Nginx, route `location /sites/` to `http://127.0.0.1:3001`
without stripping the prefix, preserving `Host`. A custom-domain server block
should proxy its entire root to that same publication reader, not to the web app.
Provision that domain's TLS separately; the included automatic certificate workflow
is for Caddy. Do not run both proxies on the same public ports.

## Operations and contributor boundaries

Take a paired database/blob backup before upgrading. The backup manifest includes
publication files, and failed/draft-release cleanup uses the existing durable blob
queue. Never expose the raw storage directory. Stop old writers, apply forward
migrations, and start matching web/sync/worker/publish versions; see
[deployment](DEPLOYMENT.md) and [native installation](NATIVE_DEPLOYMENT.md).

Contracts live in `packages/shared/src/sites.ts`; API authorization/review in
`sites-api.ts`; snapshot rendering/builds in `site-render.ts` and `site-worker.ts`;
manifest-only serving/export in `site-http.ts`. `apps/publish/client` is a separate
bundle with no workbench React tree, account stores or editing providers. Do not
replace explicit asset selection with automatic crawling, or inject untrusted
website CSS/HTML into the private application.

See [verification](VERIFICATION.md) for executed checks. Real custom DNS,
certificate issuance/renewal, container backup/restore and large/cross-browser public
reader acceptance are deployment gates, not claims established by local fixtures.
